### S2 — Deterministic artifact generation

- **User/system value**: turns the upstream token and recipe contracts into the three stable outputs downstream seams require: runtime CSS, typed token output, and the Figma-facing export.
- **Scope (in/out)**:
  - In: Style Dictionary configuration; `@tokens-studio/sd-transforms`; recipe-aware transforms; deterministic serialization for CSS, TS, and Figma JSON outputs under `design-tokens/dist/**`
  - Out: consumer adoption in app or Storybook; Figma sync-policy docs; merge-gate enforcement
- **Acceptance criteria**:
  - `pnpm build:tokens` emits the full artifact set from canonical JSON.
  - A second build with unchanged sources produces no diff.
  - Artifact ordering and serialization are stable enough for Git-based review and downstream parity checks.
- **Dependencies**: `S1`, `SEAM-1/CT-1`, `SEAM-1/CT-2`, `SEAM-2/CT-3`
- **Verification**: run the build twice with no source changes; inspect `design-tokens/dist/**` for stable CSS, TS, and Figma outputs.
- **Rollout/safety**: keep artifact generation deterministic and isolated from downstream adoption so failures are local to build inputs.

#### S2.T1 — Configure Style Dictionary for canonical token sources

- **Outcome**: the build pipeline can ingest `CT-1` and `CT-2` from the agreed source tree and emit stable base token outputs.
- **Inputs/outputs**:
  - Inputs: `design-tokens/src/tokens/**/*.tokens.json`, theme files such as `design-tokens/src/tokens/themes/dark.tokens.json`
  - Outputs: `design-tokens/build/style-dictionary.config.mjs` and any transform/filter helpers needed for v1 themes
- **Implementation notes**: apply `@tokens-studio/sd-transforms` before Style Dictionary output; keep theme handling explicit so added themes remain additive instead of changing existing theme IDs.
- **Acceptance criteria**: the config reads the canonical token tree, supports the required `dark` theme, and produces stable CSS/token intermediates without hidden cwd assumptions.
- **Test notes**: run the build twice and compare outputs; add a fixture or smoke check covering theme resolution.
- **Risk/rollback notes**: isolate theme and path assumptions inside build config so future workspace moves or extra themes do not leak into downstream consumers.

Checklist:

- Implement: add Style Dictionary config and transform helpers under `design-tokens/build/`.
- Test: run `pnpm build:tokens` twice and confirm no diff in generated intermediates.
- Validate: confirm the required `dark` theme resolves correctly and extra themes remain additive.
- Cleanup: remove any one-off transform code that duplicates upstream token semantics.

#### S2.T2 — Generate typed token output from tokens and recipes

- **Outcome**: the seam publishes a stable typed artifact at `design-tokens/dist/tokens.ts` that downstream consumers can import without reading raw source JSON.
- **Inputs/outputs**:
  - Inputs: token outputs from `S2.T1`, recipe manifests from `CT-3`
  - Outputs: `design-tokens/dist/tokens.ts` and any generator helper under `design-tokens/build/`
- **Implementation notes**: include only seam-owned typed outputs here; do not move Storybook or app adoption into this task. Keep serialization deterministic and avoid embedding absolute paths or timestamps.
- **Acceptance criteria**: the generated TS artifact contains stable exported structures/types derived from tokens and recipes; repeated builds produce byte-for-byte identical output.
- **Test notes**: compare two successive generated files; add a fixture or snapshot that proves recipe-derived sections change only when the source manifest changes.
- **Risk/rollback notes**: if the recipe schema evolves, only the generator logic and validator need to move; downstream import paths stay fixed.

Checklist:

- Implement: add the TS artifact generator and wire it into `pnpm build:tokens`.
- Test: run a deterministic snapshot or diff check on `design-tokens/dist/tokens.ts`.
- Validate: confirm recipe-derived exports match the current `CT-3` schema without inventing new recipe ownership.
- Cleanup: strip any non-deterministic metadata from the generated file.

#### S2.T3 — Emit the stable Figma-facing export artifact

- **Outcome**: `SEAM-5` receives the repo-owned artifact it needs at `design-tokens/dist/figma/tokens.json`.
- **Inputs/outputs**:
  - Inputs: canonical tokens and theme contract from `S2.T1`
  - Outputs: `design-tokens/dist/figma/tokens.json`
- **Implementation notes**: serialize keys deterministically and keep the export shape explicit; this slice owns the artifact, not the sync transport or Figma policy.
- **Acceptance criteria**: the Figma export is generated by `pnpm build:tokens`, respects the v1 theme contract, and is stable across repeated runs.
- **Test notes**: compare export diffs across repeated builds and validate the output shape against a checked-in fixture or schema.
- **Risk/rollback notes**: by separating artifact generation from sync policy, `SEAM-5` can change transport decisions without changing `SEAM-3` ownership.

Checklist:

- Implement: add the Figma export generator to the build pipeline.
- Test: verify `design-tokens/dist/figma/tokens.json` is byte-stable across repeated runs.
- Validate: confirm the export reflects only repo-authored tokens and theme IDs from `CT-2`.
- Cleanup: remove temporary debug output or intermediate export files not part of the public artifact contract.
